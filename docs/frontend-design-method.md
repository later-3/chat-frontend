# 从业务关系到界面：Chat 前端设计与实施规范

版本：1.0；2026-09-30。适用于所有新增、修改和评审的前端功能。本文规定**如何推导设计及留下证据**；[UI/UX 规范](./ui-ux-guidelines.md)规定组件、尺寸、交互与无障碍合同；[开发指南](./development.md)规定工程实现。三者共同使用，不在页面或 Skill 中复制另一套规则。

## 1. 先回答问题，再选择视觉

任何前端开发都必须先在仓库文档中记录以下分析，然后实施。新场景在 `docs/design/` 建立设计记录；已有场景更新原记录。小修改可以是一段分析加一张表，不要求每次制作全产品信息地图。聊天里的讨论、Skill 执行记录和代码注释不能代替这份记录。

| 步骤 | 必须回答 | 产物及进入下一步的条件 |
| --- | --- | --- |
| 1 任务 | 谁在什么场景，要对哪个对象完成什么事？成功是什么？ | 一句任务描述、入口和退出路径；不得从“加一个按钮”起步 |
| 2 信息 | 为完成任务，需要看到/输入/选择哪些信息？ | 信息清单：名称、来源、可读/可写、范围、频率、状态 |
| 3 关系 | 包含、次序、依赖、继承、作用域、主次分别是什么？ | 关系表或小图；事实由哪个 Backend 合同提供；未知项明确标注 |
| 4 表达 | 每种关系怎样成为导航、分组、字段、反馈？ | 关系 → 表达 → 原因的对应表，以及窄屏替代方式 |
| 5 参考 | 哪个参考解决同一种问题？哪些部分不适用？ | 具体来源、借鉴点、适配决定；不以“参考苹果”代替分析 |
| 6 实现 | 哪些共享组件与 Token 承载这些关系？ | 数据流、组件映射、保存/取消/失败/恢复与外观组合 |
| 7 验收 | 用户能否完成任务，是否知道结果与影响？ | 同状态前后截图、真实交互、必要回归、未验证项 |
| 8 回写 | 哪条推导被真实页面证实或推翻？ | 修订本案例或公共规范；可重复问题进入共享组件/测试 |

数据读取失败不能变成空列表或“继承默认”；模型目录缺字段不能猜成不支持。界面的优雅必须建立在事实正确之上。

### 最小设计记录模板

```markdown
# 功能名称
任务与入口：谁、对象、目标、离开后返回哪里。
当前问题与证据：实际场景、截图、影响，区分事实与判断。
信息清单：信息 / 来源 / 读写 / 保存范围 / 优先级 / 状态。
关系推导：关系 / 表达 / 选择原因 / 窄屏表达。
参考与取舍：来源 / 借鉴 / 不照搬的部分。
实施映射：共享组件、API、草稿与持久化、主题 Token。
验收：成功、失败、恢复、键盘、窄屏、明暗、实际截图。
修订：发现、规范或组件的调整、下一批范围。
```

## 2. 把关系表达出来

| 信息关系 | 首选表达 | 应避免 |
| --- | --- | --- |
| 集合 → 选中对象 → 属性 | 列表—详情；标题持续说明当前对象 | 每个对象展开一套长表；切换后留下旧对象数据 |
| 有顺序的步骤 | 有序列表、编号、连接线；类型和职责可辨认 | 藏在一行箭头文本；把人工审核画成模型 Agent |
| 同一对象的独立属性组 | 少量内容标签或分节；每层采用一致分类依据 | 按组件种类分组；“模型、当前会话、JSON、更多”混排 |
| 继承 → 显式覆盖 → 最终值 | 继承选择旁显示生效值与来源，提供字段级恢复 | 用有效值冒充用户已保存值；清一个字段却重置全部 |
| 作用域不同 | 操作附近标明“本项目/助手 Home/当前会话/共享模型” | 只在帮助文档解释；把全局模型定义当成单节点参数 |
| 依赖与可用性 | 按目录能力提供选项；不可用值保留且解释原因 | 对所有模型展示相同 Thinking 等级；默默换值 |
| 主结果与诊断 | 主结果在前，来源/路径/revision 按需展开 | 让路径、内部 ID 和 JSON 占领普通编辑首屏 |
| 临时聚焦 → 返回 | 共享 Dialog；嵌套编辑保留父草稿与焦点 | 每次跳转新页面；叠层后忘记正在编辑哪个对象 |
| 更改 → 接受 → 生效 | 保存状态、失败原因、重试；说明下一轮生效 | 乐观显示“已保存”；自动保存与手动提交混用而不说明 |

“折叠”只减少暂时不需要的细节，不承担主要信息架构。首屏必须回答：我在哪、改谁、能改什么、影响哪里。一个正常阅读顺序比十种装饰更重要。

## 3. 典型案例：工作流配置

### 3.1 场景与边界

用户在项目会话或长期助手设置中，选择一个工作流节点，调整下一次执行所使用的模型、指令与资源，检查最终装配。两个入口共用 `WorkflowAgentConfigDialog`，助手的持久执行配置归属自己的 Home；身份、日程和 Memory 不因此变成 Workflow 字段。

Backend 提供 Workflow、Node、Agent、模型目录和 inspection；Frontend 只拥有选中节点、分类、展开状态与草稿。当前合同见父仓库 [配置说明](../../docs/configuration/README.md)。

```text
项目 Session / 助手 Home
  └─ Workflow（一次执行组织）
       ├─ Node 01 → 工作 Agent → 主答复
       └─ Node 02 → 会话记忆 Agent → 判断是否维护本会话记忆
                     ├─ 模型与思考等级
                     ├─ 工具、Skill、Extension、Plugin
                     └─ 配置文件、Prompt 资源及会话选择
```

这是“直接执行”的例子，不能硬编码成所有 Workflow 都有两个节点。规划执行还包含人工审核 Task；节点清单不等于实际运行轨迹，记忆节点可按策略跳过。日终总结属于独立定时工作，不混入此关系。

### 3.2 信息清单与真实能力

| 信息 | 事实来源 | 用户操作及保存语义 | 优先级 |
| --- | --- | --- | --- |
| 工作流名称、用途、节点次序/类型 | Workflow summary | 结构只读，选择要配置的 Agent 节点 | 首屏 |
| 模型、Thinking | inspection + model catalog | 立即保存当前项目/Home 的节点配置；下次运行生效 | 首屏 |
| 有效值、来源、继承 | Backend resolver inspection | 查看，逐字段恢复默认；不能前端再算一遍 | 模型旁 |
| 图片输入、窗口和输出上限 | 共享模型目录 | 只读能力；编辑进入“模型参数”并说明全局影响 | 模型旁 |
| 工具、Skill、Extension、Plugin | Backend catalog/inspection | 复用持久配置 API；策略与可选项一起展示 | 第二分类 |
| Rule/Experience、配置文件、资源覆盖 | `AgentConfigSelection` | 项目会话随下一条消息提交；助手入口保存默认选择 | 第三分类 |
| 装配后的 Prompt、路径、来源、诊断 | inspection | 只读检查，不是一张另行保存的表 | 明确的检查入口 |

当前公共 Session selection 没有内联模型/Thinking/生成参数字段；温度等仍属于共享模型配置。原型中的单节点采样表单是探索，不能复制成虚假生产能力。第三分类暂按真实保存范围命名“会话调整/默认选择”；等公共合同支持按内容完全归一后，再合并为“指令与输出”。这是本轮从原型进入真实产品的第一次规范修订。

### 3.3 从关系推导布局

| 推导 | 实际表达 | 为什么 |
| --- | --- | --- |
| Workflow 包含有序 Node，Node 不全是 Agent | 左侧显示完整编号节点清单；Task 只读、Agent 可选择 | 能看见流程全貌，又不会给审核 Task 伪造模型设置 |
| 当前对象有多组属性 | 右侧对象标题 + 模型、工具与资源、会话/默认选择 | 切换节点保留分类，避免每次回到长表起点 |
| 配置值与实际装配不同 | 检查独立为只读入口；继承值就近展示 | 用户区分“我设置了什么”和“下一轮会得到什么” |
| 持久范围与入口有关 | 页首范围摘要、分类内具体保存说明 | 不让助手 Home 默认值被误认为仅影响当前 Session |
| 高级路径低频 | 配置文件折叠；已选资源和可读标题优先 | 普通用户先看到行为、专家仍可访问完整能力 |
| 屏幕变窄 | 节点区变为横向有序列表，详情独立滚动；表单单列 | 不缩小字号，也不让正文横向溢出 |

### 3.4 为什么这版比之前好

原先的问题并非缺少 CSS 技巧：字段堆叠、保存范围混淆、层级近似、折叠行空白过大，用户先看到控件而非任务。新版先建立“工作流 → 节点 → 属性”的稳定骨架，再统一视觉，所以更清晰。

- **适度加粗**：Chat 品牌、页面标题、当前节点承担不同层级。标题 600–650，正文 400，辅助文字用尺寸和颜色降低权重；不能把每行都加粗。
- **黑底白形品牌标记**：高对比的小面积轮廓形成稳定定位点；品牌有重量，周围正文可以安静。不是把所有按钮涂黑。
- **有目的的留白**：组间大于组内，字段标签紧贴字段，节点说明跟随节点；不用空白撑出“高级感”。
- **克制色彩**：强调色指示当前选择与主动作；成功/失败仍用独立语义色。玻璃、高光和渐变不能替代可访问名称或状态说明。
- **一致组件**：同一种动作始终用共享 Button，同类临时编辑用 SurfaceDialog；只有用途不同才改变表达。

Skill 能查焦点、性能和 Token，但无法替产品决定“哪个对象是谁、这次保存影响哪里”。此前直接从 Skill 的风格建议跳到 CSS，缺少第 2、3、4 步；以后以关系表和实际任务验收补上这个缺口。

## 4. 外部规范与 Skills 怎样结合

下表是 Chat 的适配判断，不是宣称产品经过 Apple/Google 认证，也不要求同时混用两家的组件库。

| 来源 | 可借鉴的原则 | 在本例中的落实与边界 |
| --- | --- | --- |
| [Material 3 canonical layouts](https://m3.material.io/foundations/layout/canonical-examples/overview) | 列表—详情及不同宽度适配 | 节点导航和属性详情；不照搬移动端大卡片密度 |
| [Material foundations](https://m3.material.io/foundations/) / [design tokens](https://m3.material.io/foundations/design-tokens/overview) | 状态、内容设计和可复用样式值 | 表单八类状态与语义 Token；不是换一组鲜艳背景就叫 Material |
| [Apple design principles](https://developer.apple.com/design/human-interface-guidelines/design-principles) / [layout](https://developer.apple.com/design/human-interface-guidelines/layout) | 清楚的层级、对齐与可适应布局 | 标题、节点、辅助信息各有层级，窄屏仍可操作 |
| [Apple materials](https://developer.apple.com/design/human-interface-guidelines/materials) | 材质区分控件层与内容层 | 玻璃主要用于导航和浮层外壳；文本与表单维持可靠底色。CSS 模糊是 Web 近似，不宣称原生 Liquid Glass |
| [WCAG 2.2 contrast](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) | 普通文本至少 4.5:1，大字至少 3:1 | 每套明暗配色验证文字；透明效果按合成后背景验收 |
| 本地 [web-design-guidelines](../.agents/skills/web-design-guidelines/SKILL.md) | 键盘、焦点、标签、错误、减少动效 | 在关系与组件确定后执行质量门禁，不代替业务分析 |
| 本地 [react-best-practices](../.agents/skills/react-best-practices/SKILL.md) | 请求、渲染、资源与状态管理 | 节点切换取消旧请求；主题变化不重建表单、不清草稿 |
| `ui-ux-pro-max`（安装时可用） | 备选风格与常见反例检索 | 只作为素材；营销站默认建议不自动适用于 Chat 工具页 |

用户提供的 littleplains、Aside、Resurf、Daybridge 与 Cherry Studio/Pi Web 的观察见[打样记录](../../docs/history/reviews/2026-09-30-agent-configuration-information-design.md)。网站参考用于字重、密度、对齐和层次；产品参考用于信息分组与交互；均不能替 Chat 定义执行和保存合同。

## 5. 全局外观是可组合的基础

```text
业务结构与可访问语义（不随外观变化）
  → 基础：排版、间距、组件、状态、布局
  → 模式：浅色 / 深色 / 跟随系统
  → 配色：经典 / 海蓝 / 桃雾 / 兰紫 / Instagram
  → 材质：纸质 / 玻璃
  → 效果偏好：背景、减少透明、减少动效
```

配色定义语义色，材质定义表面、边缘、阴影、圆角与透明度；动效只说明状态变化。纸质可以海蓝，玻璃也可以经典。原型七套是组合示例，不是七套互相独立的运行时；未来预设只能给这些轴赋值，不能私藏组件 CSS 或锁死组合。

- 默认基础沿用经典配色、纸质、系统明暗；品牌、字重、阅读节奏和必要状态反馈属于所有外观共同基础。
- 全局外观入口在“设置 → 外观”；应用根节点一次应用，导航、按钮、输入、弹窗及 Portal 使用同一套语义 Token。页面不得另建主题状态或硬编码自己的主色。
- 外观仅保存浏览器偏好，不写项目/Agent 配置，不上传服务器。刷新恢复；存储不可用仍可使用，不能崩溃；系统设置变化只影响 auto。
- 系统减少动效优先于个人选择；手动减少动效也关闭主题圆形揭示。关闭背景不移除表单底色；减少透明保留配色但恢复实色。无 `backdrop-filter` 支持应自然降级。
- 玻璃的层数受限，不为每个字段添加独立模糊，不动画 blur、不在正文上放持续运动背景。阴影表达浮起，不给所有内容套卡片。
- 共享 Button/控件的交互角色、触控尺寸、焦点和 disabled 语义固定；材质仅通过 Token 调整外观，不改变操作。
- 离线页/独立历史 iframe 是独立文档，保留明确的基础明暗降级与安全合同；不能为接入主题扩大 iframe 权限。不得声称全局 Token 已人工验收所有页面。

## 6. 落地与验收门槛

每次交付必须能从设计记录找到：信息清单 → 关系推导 → 组件/合同 → 实际截图/测试。基础状态至少覆盖 default、hover、focus、pressed、selected、disabled、loading、error 中实际适用项。

Workflow 案例：检查直接执行两类节点和含审核 Task 的 Workflow；切节点/分类不丢选择，迟到结果不污染当前节点；恢复模型继承不清工具；助手默认说明正确；共享模型编辑返回保留原状态；失败可重试；Tab/方向键/Escape/焦点恢复；桌面与约 390px 窄屏，长名称，中英文，纸/玻璃、明/暗。

全局主题：各配色覆盖明暗和两种材质；组合变化不丢表单草稿；刷新、旧 `pi-theme`、非法偏好、存储拒绝、系统偏好、减少效果；菜单/嵌套 Dialog 不漏色。自动化测试和人工截图分别记录，不互相冒充。完整测试遵守开发指南及父仓库验证命令，不覆盖正在运行的正式构建。

## 7. 用真实产品迭代规范

| 优先级 | 页面/基础 | 要验证的推导 | 本轮边界 |
| --- | --- | --- | --- |
| P0 | 全局外观 + 工作流编辑器 | 可组合外观；Workflow → Node → Agent → 字段；真实保存范围 | 本轮实施，并回写 [实施记录](./design/workflow-configuration-rollout.md) |
| P1 | Long Agent 身份、能力、日程入口 | 身份与执行配置分工；同组件能否适应不同入口 | 第二轮已整理配置主区与分类职责，见[助手与聊天案例](./design/assistant-and-chat-rollout.md)；各任务/记忆内部后续细化 |
| P2 | Chat 顶栏、输入框、运行过程 | 对话、执行、后台工作和记忆的关系，操作主次 | 第二轮升级空会话与公共输入；顶栏及运行过程后续单独分析 |
| P3 | Memory、资源库、任务归档 | 集合/详情、作用域、历史/当前、权限与恢复 | 后续以具体场景逐页验证 |

修订由真实问题驱动：先修改案例中的具体推导；只有能在第二个场景复用的原则才提升为公共规则。不要每次不满意就追加一层 CSS 或换一套 Skill，也不要把待实施能力写成已发布事实。
